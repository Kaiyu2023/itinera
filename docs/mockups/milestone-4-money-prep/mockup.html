Money & “Before you go” — interactivity

Making the read-only Ledger and Before you go tabs interactive: adding & splitting expenses, seeing balances, settling up, and running group prep checklists. Content is real from the fixtures for Japan, Autumn Leaves (Nov 14–20 2026, 6 travellers, Tokyo → Hakone → Kyoto → Osaka). Signed in as Kaiyu, a trip leader. Amounts are entered in JPY; balances & settle-up show the trip’s base currency USD (fixture baseCurrency), frozen at each entry’s FX. Grey notes are rationale; extension flags a proposed type change, illustrative flags data the fixtures don’t carry yet.

Why no approval on money. Milestone 3 gates only structural plan edits (they change everyone’s itinerary). An expense is a record of something that already happened — gating it would just add friction and stale balances. So addExpense writes straight through, consistent with the governance model. The nice touch: picking a linked stop reads the stop’s kind + name to pre-seed category and note, turning a 6-field form into two taps for the common case.

✳️
Validation contract. even just needs ≥1 participant. exact must satisfy Σ participants.amount === amount in the entry currency — the remainder indicator is that equation, live. We deliberately kept the middle shares (weighted) shape out of the primary UI to avoid a third mental model; it stays in the type for API/AI callers, and “custom ¥” covers the same intent more legibly.

💡
Rounding & honesty. Transfers are the server’s min-cash-flow simplification, so six people collapse to four payments. Sub-dollar rounding is absorbed into the largest transfer so the four suggestions always sum to the exact outstanding total. Because settlements are stored in base currency (per Settlement.amount), the flow is currency-agnostic — a JPY-base trip would show ¥ here with no code change.

Progress is a group read. toggleChecklistItem is shared state, and ChecklistItem.doneBy is a set of userIds — so each row shows who’s ticked it (avatar stamps + “n / 6”), and the notice bar reports how many items the whole group has fully cleared. ✳️
NoticePatch today carries title, body, pinned, sourceUrl — so Edit and Pin are covered. Resolve / Archive need a lifecycle field: proposed extension Notice.status?: 'active' | 'resolved' | 'archived' (default active) plus NoticePatch.status?. Resolved notices grey out and drop below active ones; archived ones leave the list but stay in history. Until then those two items are illustrative.
📝
Checklist rows are just strings on create. CreateNoticeInput.checklistItems?: string[] — the backend assigns each an id and an empty doneBy. That’s why the composer’s rows are plain text inputs with no “done” state: completion is something the group does later, not something you pre-set when posting.

Shared list, per-person ticks — the honest reading of the type. doneBy: string[] means each item tracks which members have personally done it, so “add Suica to your wallet” is naturally a per-person task and the avatars show group coverage. That is what we designed to. Caveat for the reviewer: a few items are genuinely “once for the group” (e.g. “Reserve Hikari seats” — one person books for everyone). Two ways to serve both without changing the type: (1) treat an item as group-complete when doneBy.length ≥ 1 and label it “booked by Makoto”, or (2) add a proposed extension ChecklistItem.mode?: 'each' | 'group' so the row renders as a single shared checkbox with the doer’s avatar. We recommend (2) — it removes the ambiguity the “1 / 6” count creates for group tasks. Flagging rather than assuming, per the brief.
